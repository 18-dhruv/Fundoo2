# Observability: running SigNoz

How to run the SigNoz backend that the Fundoo services send OpenTelemetry data to. The design, the
reasoning behind it and how to use SigNoz are covered in [`docs/OBSERVABILITY.md`](../../docs/OBSERVABILITY.md).

| Path | What it is |
|---|---|
| `signoz/docker-compose.signoz.yml` | SigNoz (UI + query service, ingester, ClickHouse, ClickHouse Keeper, Postgres metastore). Generated by SigNoz Foundry v0.5.0 from `signoz/casting.yaml`, with image tags pinned (`signoz/signoz:v0.150.0`, `signoz/signoz-otel-collector:v0.144.15`, `clickhouse:25.12.5`). |
| `signoz/ingester/`, `signoz/telemetry*/` | Config files mounted by that compose file (unchanged Foundry output). |
| `dashboards/fundoo-services.json` | The "Fundoo services overview" dashboard (SigNoz schema v6). |
| `alerts/fundoo-high-error-rate.json` | Example alert: a service's error rate above 5% over 5 minutes. |
| `../k8s/30-observability.yaml` | In-cluster OpenTelemetry Collector. The services send to it, and it forwards to SigNoz. |

## Local development

```bash
docker compose -f deploy/observability/signoz/docker-compose.signoz.yml up -d
```

1. Open http://localhost:8080. On first start, create the admin account. **Nothing is ingested until
   that account (the organisation) exists**: until then the ingester gets no config and rejects OTLP.
2. Start the app infrastructure (`docker compose --profile mail up -d` in the repo root: Kafka, Redis and
   Mailpit) and run the services with `dotnet run`. They send OTLP to `http://localhost:4317` by default,
   so no configuration is needed.
3. Optional: to see metrics sooner, set `OTEL_METRIC_EXPORT_INTERVAL=10000` (in milliseconds; the default is 60 s).
4. Import the dashboard: **Dashboards → New dashboard → Import JSON**, then paste `dashboards/fundoo-services.json`.
5. Optional, for the alert: create a notification channel named `fundoo-team` (**Settings → Notification
   channels**), then **Alerts → New alert → Import** with `alerts/fundoo-high-error-rate.json`. Both can
   also be created through the API (`POST /api/v2/dashboards`, `POST /api/v2/rules` with a bearer token
   from `POST /api/v2/sessions/email_password`). That is how they were tested.

Docker needs about 3 GB RAM for SigNoz. To stop: `... down` keeps the data, and `... down -v` deletes it.
If the services run while SigNoz is down, nothing breaks: the exporters retry briefly, then drop the data.

To e-mail through the local Mailpit instead of Gmail, set these for the Notification API:
`EmailSettings__Host=localhost EmailSettings__Port=1025 EmailSettings__SecureSocketOptions=None` (any
username and password). The inbox is at http://localhost:8025.

## Production: SigNoz on a separate VM (the option chosen)

The k3s VM (2 vCPU / 7.7 GB) is already full with k3s, Kafka, Jenkins and the services. ClickHouse would
need another 2–4 GB, so SigNoz runs on its own VM in the **same VNet**. The cluster reaches it over the
private IP, and nothing is exposed publicly.

```bash
# Same variables as deploy/AZURE_DEPLOY.md. `az vm create` there made the VNet ${VM}VNET / subnet ${VM}Subnet.
SIGNOZ_VM=fundoo-signoz
az vm create -g $RG -n $SIGNOZ_VM --image Ubuntu2404 --size Standard_B2ms \
  --vnet-name ${VM}VNET --subnet ${VM}Subnet --nsg-rule NONE --public-ip-sku Standard \
  --admin-username azureuser --generate-ssh-keys --os-disk-size-gb 64
az network nsg rule create -g $RG --nsg-name ${SIGNOZ_VM}NSG -n ssh-from-me --priority 900 \
  --source-address-prefixes $MY_IP --destination-port-ranges 22 --access Allow --protocol Tcp
SIGNOZ_PRIVATE_IP=$(az vm show -d -g $RG -n $SIGNOZ_VM --query privateIps -o tsv)
SIGNOZ_PUBLIC_IP=$(az vm show -d -g $RG -n $SIGNOZ_VM --query publicIps -o tsv)
```

- Port 4317 (OTLP) is reachable from the k3s VM through Azure's default `AllowVnetInBound` rule. Don't open
  it to the internet.
- Reach the UI through an SSH tunnel rather than a public port:
  `ssh -L 8080:localhost:8080 azureuser@$SIGNOZ_PUBLIC_IP`, then open http://localhost:8080.

On the SigNoz VM, install Docker and start SigNoz:

```bash
curl -fsSL https://get.docker.com | sudo sh
git clone https://github.com/18-dhruv/Fundoo2.git && cd Fundoo2
sudo docker compose -f deploy/observability/signoz/docker-compose.signoz.yml up -d
# then create the admin account through the tunnel, as in local development
```

On the k3s VM, point the collector at it. This writes the `fundoo/signoz-backend` secret and restarts the collector:

```bash
sudo SIGNOZ_ONLY=1 bash deploy/azure/set-secrets.sh
# SigNoz OTLP gRPC endpoint host:port: <SIGNOZ_PRIVATE_IP>:4317 ; plain-text: Y ; ingestion key: (blank)
```

The collector Deployment itself is applied by Jenkins with the rest of `deploy/` (`kubectl apply -k deploy/`).
Until the secret exists, the collector runs and drops what it can't deliver.

**Switching to SigNoz Cloud later** needs no code or image change. Re-run the same command with
`ingest.<region>.signoz.cloud:443`, answer **n** to plain-text, and paste the ingestion key.

## Retention

SigNoz keeps traces and logs for 15 days and metrics for 30 days by default. Change this under
**Settings → General → Retention**. With a 64 GB disk, 15 days of this app's volume is comfortable.
